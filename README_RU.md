# StrixArc

**Metal на AMD Radeon 880M / 890M (Strix Point, RDNA 3.5, GC 11.5.0) для macOS Sequoia 15.**
Запуск GPU, вывод изображения, на котором WindowServer композитит силами GPU, и Metal поверх Vulkan (Mesa RADV).

StrixArc — порт [nullarc](https://github.com/luuumi-dev/nullarc) (Radeon 780M, Phoenix) на Strix Point. Имена
компонентов (PhxBringup, PhxAccel, NVMTLDriver) и лицензии взяты из nullarc, см. [LICENSE](LICENSE). Проект не связан
с nullarc и не одобрен его авторами.

> [!WARNING]
> **Проверено ровно на одной машине**: ноутбук автора Lenovo с Radeon 880M (Strix Point), macOS 15.8.1, загрузка через
> OpenCore с флешки. Больше этот код нигде не запускался. **Нет никакой гарантии, что драйвер заработает у вас — или
> вообще**: он напрямую программирует загрузчик прошивок GPU, контроллер памяти и дисплейный движок, и ошибка может
> повесить Мак, вызвать kernel panic или оставить экран чёрным до перезагрузки. Используйте, только если умеете из
> этого выбраться (загрузка с другого EFI, boot-arg `-phxbringupoff`, см. [флаги и откат](#флаги-и-откат)). Всё
> «как есть», без каких-либо гарантий.

## Состояние (октябрь 2026, ноутбук Lenovo с Radeon 880M, панель 3072x1920 30–120 Гц, macOS 15.8.1)

| | |
|---|---|
| **Запуск GPU** | PSP (с TMR от драйвера), SMU, RLC, MES + KIQ, очереди compute и gfx — при каждой загрузке (`phxboot`, со страховками). |
| **Metal** | работает в приложениях; WindowServer композитит на GPU. |
| **Экран** | родные 3072x1920 при **120 Гц** (v0.2.0): при загрузке линк eDP перетренировывается с 4,32 Гбит/с прошивки на 8,1 Гбит/с через DMCUB, до того как WindowServer откроет экран. Кадр копирует **SDMA** в один из двух буферов видеопамяти (0,84 мс на кадр 3K), экран переключается на него по vsync: ~120 fps, без разрывов, процессор в копировании не участвует. |
| **Видео** (v0.2.5) | H.264 и HEVC (8/10 бит, проверено до 4K) декодируются на видеоблоке GPU (VCN 4.0.5) через Vulkan Video в RADV — побитово так же, как программный декодер, — в FFmpeg 8.1 и его плеере: `vplay <файл>` или **VCN Player.app** из Finder («Свойства» → «Открыть в программе»). 4K: ~3,5 с процессора на 10-секундный ролик вместо 12,2 с, без пропущенных кадров. VCN поднимается при загрузке; `sysctl debug.phxvcn_jobs` и `~/Library/Logs/vplay.log` показывают, что декодирует VCN. Safari, QuickTime и другие плееры через VideoToolbox пока декодируют на процессоре. |
| **Пока нет** | аппаратный декод для VideoToolbox (Safari, QuickTime), кодирование видео, внешние мониторы, подсветка, переменная частота. Некоторые тяжёлые анимации (открытие папок в Launchpad) пока проседают заметно ниже 120 fps. |

## Производительность

`fps_check.sh` на машине автора, 3072x1920: тестовое окно (`fpsanim`) двигает квадрат каждые 1/120 с в течение 6 с, мышь
не трогаем; показанные кадры и время кадра в конвейере вывода — счётчики PhxAccel, загрузка WindowServer — `top` за
время замера (в процентах одного ядра).

| Версия / способ | Частота | Показано кадров | На кадр в конвейере вывода | CPU WindowServer |
|---|---|---|---|---|
| до SDMA: копирует процессор через BAR | 60 Гц | 30,8 fps | 19,2 мс (само копирование) | 8,5–9,9 % |
| v0.1.0: копия SDMA + переключение по vsync | 60 Гц | 61,8 fps | 7,1 мс (в основном ожидание прошлого переключения) | 13,6 % |
| **v0.2.0: копия SDMA + переключение по vsync** | **120 Гц** | **121,8–122,3 fps** (окно: 119,1–119,6 сдвигов/с) | **2,0–2,5 мс** | **26–47 %** |

Само копирование кадра 3K движком SDMA — 0,84 мс (28 ГБ/с); остальное время кадра — ожидание работы GPU до кадра,
прошлого переключения и проверка 32 точек. Счётчик показанных кадров чуть выше частоты, потому что счётчики читаются за
6 с плюс время самого чтения; счёт самого окна точный. macOS показывает панель как «3072 x 1920 @ 120.00Hz», AppKit
видит 120–121 fps.

Подробности со всеми замерами — в [docs/strix-point.md](docs/strix-point.md) (англ.).

## Отличия от nullarc

nullarc сделан для Radeon 780M (Phoenix, GC 11.0.1) под macOS Tahoe 26. StrixArc сохраняет его устройство и меняет:

| | nullarc (780M) | StrixArc (880M) |
|---|---|---|
| GPU | GC 11.0.1, PCI 1002:1900 | GC 11.5.0, PCI 1002:150E; регистры GCVM переводятся по таблице (`src/amd/rdna3_chip.h`), MES получает базы IP от Strix |
| PSP | 13.0.4, TMR держит прошивка | 14.0.0: TMR выделяет драйвер (`SETUP_TMR`, 0x8900000 байт в 512 МиБ от верха видеопамяти), план загрузки прошивок читается из заголовков (`fwplan`), кольцо PSP на 48 МиБ (вне кадра 3K) |
| Сброс HDP | через регистр remap NBIO | в NBIO 7.11 он за пределами BAR5: сброс напрямую через `BIF_BX_PF1_HDP_MEM_COHERENCY_FLUSH_CNTL` |
| Ошибки VM | останавливают клиента | по умолчанию уводятся на пустую страницу (CP gfx читает один неотображённый адрес на первом IB каждого нового VMID) |
| Частота | прошивка 780M сама включает панель на родных 120 Гц | загрузчик (GOP) включает панель 880M на 60 Гц (4,32 Гбит/с); при загрузке `mesboot hz 120` перетренировывает линк на 8,1 Гбит/с через DMCUB загрузчика (команды передатчика VBIOS, клоки дисплея через SMU, DTO и DLG под 120 Гц), PhxAMDFB заново измеряет панель ([ниже](#120-гц-как-работает-переключение)) |
| Экран | кадр копирует процессор в carve-out (на 780M это быстро), 120 Гц | запись процессора в carve-out ~55 МБ/с, через BAR ~600 МБ/с (кадр 3K: 20–37 мс), а DCN 3.5 не читает ОЗУ (rIOMMU под macOS выключен): **кадр копирует SDMA во второй буфер, экран переключается на него** (ниже) |
| Разрешение | как у прошивки | родные 3072x1920 через OpenCore `UEFI > Output > Resolution = Max` (раньше прошивка растягивала 1920x1200) |
| macOS | Tahoe 26 | Sequoia 15 (сборка PhxAccel не для Tahoe) |
| Сборка | Xcode на Маке | ещё и в Linux: обычный clang + ld64 из cctools-port (`tools/cross/build-macos.sh`; своя `__cxa_atexit`, без fortified-вызовов libc) |
| Mesa | заготовка `phoenix` | патч 0007: GC 11.5.0 и заготовка `strix1` |
| Загрузочный демон | phxboot | плюс: переключение на 120 Гц до того, как WindowServer откроет экран; SDMA с первого кадра WindowServer; зависание в первую минуту после любого из них выключает только его; обычная перезагрузка не считается зависанием; логи каждой загрузки сохраняются |

## SDMA: как работает и когда отключается

PhxBringup сам ведёт очередь 0 движка SDMA0 (кольцо по адресу 0x6000000 видеопамяти, VMID 7 со своими таблицами
страниц, два буфера кадра по 32 МиБ на 0x8000000 и 0xA000000). На каждый кадр WindowServer, при
`debug.nvaccel_iop_gpucopy=1`:

1. ждёт, пока GPU закончит работу, отправленную до кадра (не дольше 50 мс; дальше кадр копируется как есть, счётчик
   `phxscanout_gpulate`) — WindowServer отдаёт кадр раньше, чем GPU его дорисовал;
2. ждёт, пока прошлое переключение вступит в силу (не дольше 25 мс; иначе кадр пропускается, `phxscanout_busy`);
3. один `COPY_LINEAR` всего кадра в буфер, который сейчас не на экране, сброс GL2 и fence;
4. сверяет 32 точки копии с кадром (через отображение кадра в PhxAccel, со сбросом кэша);
5. переключает конвейер 0 DCN на этот буфер — срабатывает на ближайшем vblank.

| Что случилось | Что будет |
|---|---|
| исходный пиксель ещё меняется (GPU дорисовывает кадр) | кадр пропущен, на экране остаётся прошлый (`phxscanout_moving`) |
| скопированный пиксель неверный | кадр пропущен (`phxscanout_mismatch`, `phxscanout_lastbad`); **8 подряд — выключение до перезагрузки** |
| копия не закончилась за 50 мс | SDMA остановлен и сброшен, **выключение до перезагрузки** |
| underflow конвейера 0, сменился размер кадра или кадр прошивки | **выключение до перезагрузки** |
| SDMA0 не запустился, буферы не отобразились | **выключение до перезагрузки** |

При выключении на экран сначала возвращается кадр прошивки, дальше до перезагрузки копирует процессор (около 30 fps
в 3K). `sysctl debug.phxscanout_state` — `on` или причина выключения; `debug.phxscanout_copies`, `_us_sum`,
`_gpuwait_us`, `_busy`, `_moving`, `_mismatch`, `_lastbad` — остальные счётчики. `sudo sysctl -w
debug.nvaccel_iop_gpucopy=0` в любой момент возвращает копирование процессором. `bash tools/phxctl/fps_check.sh`
(в раунде проверки — `go.sh`) меряет оба способа.

## 120 Гц: как работает переключение

Прошивка (GOP) тренирует линк панели на 4,32 Гбит/с (индекс 5 в таблице частот eDP 1.4) — этого хватает только на
60 Гц. `mesboot hz 120` делает то же, что Linux DC на этом ноутбуке (записано под Linux, `tools/linux-trace`), через
DMCUB, который оставил работать загрузчик:

1. клоки дисплея через SMU: DISPCLK 800 МГц, DPPCLK 782 МГц, DCFCLK в глубоком сне 55 МГц;
2. гашение: DPG чёрный, подсветка выкл., поток, OTG и DIG выкл., приёмник в D3, передатчик выкл., питание панели выкл.;
3. тайминги: `DP_DTO0_PHASE` вдвое, DLG/TTU конвейера из значений прошивки для 60 Гц с временными полями пополам;
4. питание панели вкл., TRANSMITTER ENABLE на symclk 810 МГц, тренировка линка на индексе 7 (8,1 Гбит/с): TPS1, TPS4,
   настройки линий, которые просит панель (размах не выше 2);
5. поток с `DP_VID_M` под новую частоту, подсветка, картинка.

Прошивка DMCUB загрузчика на каждое событие HPD сама включает PHY с настройками линка, которые ей оставил загрузчик, и
одно такое событие приходит посреди смены частоты. Поэтому `mesboot` сначала переписывает эти настройки (область 4
DMCUB, +0x5318) на новую частоту, а `hz 60` возвращает их обратно. Подробности — в [docs/strix-point.md](docs/strix-point.md).

При загрузке, если есть `$G/phxboot-120`, phxboot делает это, пока PhxAMDFB ещё держит WindowServer, потом
`sysctl debug.phxfb_remeasure=1` — PhxAMDFB заново измеряет панель, и режим и таймер vblank уже говорят 120 Гц, когда
WindowServer открывает экран.

| Что случилось | Что будет |
|---|---|
| переключение не удалось (нет захвата на 8,1 Гбит/с, DMCUB перестал принимать команды) | обратно на 60 Гц тем же путём, `phxboot-120` удаляется (дальше 60 Гц) |
| не удался и возврат (экран остался тёмным) | phxboot перезагружает Мак; загрузчик снова включает панель на 60 Гц |
| зависание или зажатая кнопка питания на тёмном экране в первые 90 с WindowServer | на следующей загрузке найдётся `hz120.pending`: `phxboot-120` удаляется |

`bash gpu/hz_test.sh` переключает 60 -> 120 -> 60 Гц вручную (с журналом каждой команды DMCUB); `bash gpu/hz_ws_check.sh`
сверяет линк, PhxAMDFB, настройки дисплея macOS и счётчики кадров на 120 Гц.

## Флаги и откат

Флаги — файлы в `/Users/Shared/gpu` (`$G`), их читает загрузочный демон (что он сделал — в `/var/log/phxboot.log`).
Имена скриптов — как в папке раунда; в репозитории Strix-версии лежат как `tools/phxctl/*_strix.sh`.

| Флаг | Значение | Кто ставит / как снять |
|---|---|---|
| `phxboot-off` | аварийный выключатель: phxboot ничего не делает, GPU выключен | ставится сам, если загрузка не прошла запуск GPU или проверку WindowServer; снимает `sudo bash install_boot.sh` (или `go.sh`) |
| `phxboot-m2` | WindowServer на GPU (панель берёт PhxAMDFB) | `install_boot.sh --windowserver [--force]` / `--no-windowserver`; снимается сам после 3 падений WindowServer за 90 с или 3 перезагрузок из-за зависания GPU за час |
| NVRAM `phxfb-boot` | PhxAMDFB берёт панель на следующей загрузке | phxboot ставит его заново после каждой удачной загрузки; `sudo nvram -d phxfb-boot` |
| `phxboot-gpucopy` | SDMA при загрузке | создаёт `fps_check.sh`, когда SDMA прошёл проверку; `sudo rm` — назад к копированию процессором |
| `gpucopy.pending` | идёт минута наблюдения за SDMA | сам; если он остался к следующей загрузке, значит было зависание: `phxboot-gpucopy` удаляется |
| `phxboot-120` | 120 Гц при загрузке | `go.sh` создаёт его один раз для папки релиза или раунда с файлом `HZ120`; phxboot удаляет после неудачного переключения; `sudo rm` — 60 Гц |
| `hz120.pending` | переключение на 120 Гц в этой загрузке ещё не подтверждено (до конца 90 с наблюдения за WindowServer) | сам; если он остался к следующей загрузке, значит было зависание: `phxboot-120` удаляется |
| `hz60.base` | значения дисплея прошивки для 60 Гц, сохраняет первый `mesboot hz` | сам; их возвращает `hz 60` |
| `phxboot-apps` | Metal для всех приложений, когда WindowServer не на GPU | `sudo touch` / `sudo rm` |
| `phxboot-vcn` | VCN при загрузке: поднимается и передаётся PhxBringup после 90-секундной проверки WindowServer, плееры декодируют на нём | `go.sh` создаёт его один раз для релиза или раунда с файлом `VCNBOOT`; phxboot удаляет его, если VCN не поднялся; `sudo rm` |
| `vcn.pending` | VCN поднимается в этой загрузке (20 с) | автоматически; найден при следующей загрузке — значит, было зависание: `phxboot-vcn` удаляется |
| `radv.pending` | новый RADV на испытании (`update_radv.sh`): `new`, затем `tried`, когда загрузка запустила на нём WindowServer | phxboot удаляет его, когда WindowServer прошёл 90-секундную проверку; если загрузка на нём её не прошла — возвращает прежний RADV |
| `logs/*-atboot` | логи каждой загрузки через ~100 с после старта (последние 6) | сами; `nullarc_logs.sh` копирует их на флешку |

Резервные копии и откат каждого изменения:

| Что меняли | Как откатить |
|---|---|
| PhxBringup.kext в `EFI/OC/Kexts` на флешке | после каждого обновления в корне флешки лежит `EFI-backup-<дата>-build<N>/PhxBringup.kext` — скопировать обратно; boot-arg `-phxbringupoff` выключает PhxBringup целиком |
| PhxAccel.kext в Auxiliary KC | `sudo bash update_accel.sh --undo` (копии в `/Users/Shared/nullarc-backup/accel-update.*`) |
| родные 3K (OpenCore `Resolution=Max`) | `EFI/OC/config-1920x1200.plist` — прежний конфиг, скопировать поверх `config.plist` |
| загрузочный демон | `sudo bash install_boot.sh --undo` (GPU больше не запускается при загрузке) |
| режимы HiDPI | `sudo bash gpu/hidpi.sh --undo` |
| RADV (`/Library/GPUBundles/nvmtl/libvulkan_radeon.dylib`) | сам, если WindowServer не поднялся на новом; иначе `sudo bash ~/gpu/update_radv.sh --undo` и перезагрузка (копии в `/Users/Shared/nullarc-backup/radv-update.*`) |
| VCN при загрузке | `sudo rm /Users/Shared/gpu/phxboot-vcn` и перезагрузка |
| плеер (`/Users/Shared/gpu/ffmpeg`, `/usr/local/bin/vplay`, `/Applications/VCN Player.app`) | `sudo bash ~/gpu/install_player.sh --undo` |
| 120 Гц | `sudo rm /Users/Shared/gpu/phxboot-120` и перезагрузка (или только до перезагрузки: `sudo ~/gpu/phxctl/mesboot hz 60`; WindowServer до перезагрузки продолжит рисовать с темпом 120) |

## Релизный пакет

`StrixArc-<версия>.zip` (GitHub releases) — папка раунда, которую прогнала машина автора, с бинарниками ровно в том виде,
в каком их проверяли (PhxBringup, PhxAccel, бинарник NVMTLDriver, RADV, `mesboot`/`phxctl`/`fwplan`, FFmpeg/ffplay), плюс
10 файлов прошивок из linux-firmware (без изменений) и лицензии. Бандла NullMoth и его транслятора AIR в нём нет: `setup_metal.sh`
берёт их из пакета NullMoth 2.4.1. Порядок установки — в `README.txt`: PhxBringup в OpenCore, `bash install.sh`,
`sudo bash setup_metal.sh <pkgroot NullMoth> .`, `bash go.sh`, перезагрузка, ещё раз `bash go.sh`.

## Сборка и проверка

Сборка в Linux: `tools/cross/build-macos.sh <env.sh тулчейна>`. Раунд проверки — папка `nullarc/` на флешке с
OpenCore; на Маке `bash go.sh` ставит изменившееся, просит перезагрузку, когда она нужна, иначе запускает тесты раунда,
логи сами ложатся на флешку (`nullarc_logs/`).
